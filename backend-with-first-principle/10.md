# 10. Controllers, Services, Repositories, Middlewares, and Request Context

---

# Introduction

Modern backend applications are rarely written as one large file containing all logic. As applications grow, developers divide responsibilities into separate layers and components. This architectural pattern is known as **Separation of Concerns (SoC)**.

The main goal is to ensure that each component has a clear responsibility, making the code:

- Easier to maintain
- Easier to debug
- Easier to scale
- Easier to test
- Easier for teams to collaborate on

A typical backend request travels through the following flow:

```text
Client
   │
   ▼
Middlewares
   │
   ▼
Controller
   │
   ▼
Service
   │
   ▼
Repository
   │
   ▼
Database
```

The response then travels back in the reverse direction.

---

# 1. Backend Architecture Pattern

When a client sends an HTTP request, the server processes it through multiple layers.

Instead of placing all logic inside one function, backend systems commonly separate code into:

1. Controllers
2. Services
3. Repositories
4. Middlewares
5. Request Context

This design follows the **Single Responsibility Principle (SRP)**, where every layer performs one specific job.

## Example Scenario

Suppose a user wants to create a new book.

```http
POST /books
```

Request Body:

```json
{
  "title": "Clean Code",
  "author": "Robert C. Martin"
}
```

Request Flow:

```text
Client
 ↓
Middleware
 ↓
Controller
 ↓
Service
 ↓
Repository
 ↓
Database
```

Each layer contributes something different.

---

# 2. Controller Layer (Handler Layer)

## Definition

A Controller is the entry point of an API endpoint after routing matches the URL.

Its responsibility is to:

- Receive requests
- Extract data
- Validate input
- Call services
- Return responses

Controllers should contain very little business logic.

---

## Responsibilities of a Controller

### 1. Data Extraction

Controllers extract information from:

- URL parameters
- Query parameters
- Headers
- Request body

Example:

```http
GET /books?id=10
```

Controller extracts:

```javascript
const id = req.query.id;
```

For POST requests:

```javascript
const body = req.body;
```

---

### 2. Binding (Deserialization)

Data over the internet travels as text (usually JSON).

The controller converts it into native objects.

JSON:

```json
{
  "name": "John"
}
```

Becomes:

```javascript
{
  name: "John"
}
```

or

```go
type User struct {
    Name string
}
```

If conversion fails:

```json
{
  "name":
}
```

Return:

```http
400 Bad Request
```

---

### 3. Validation

Controllers validate incoming data.

Checks include:

- Required fields
- Data types
- String lengths
- Email formats
- Numeric ranges

Example:

```json
{
  "email": ""
}
```

Invalid because email is empty.

Return:

```http
400 Bad Request
```

---

### 4. Transformation

Controllers may modify data before passing it forward.

Example:

Client request:

```http
GET /books
```

No sort parameter provided.

Controller adds default:

```javascript
sort = "created_at";
```

Result:

```javascript
{
  sort: "created_at"
}
```

---

### 5. Delegation

After validation, the controller delegates work to the Service Layer.

Example:

```javascript
bookService.createBook(data);
```

The controller should not contain business logic.

Bad:

```javascript
if(user.age > 18){
   // business logic
}
```

Good:

```javascript
userService.register(user);
```

---

### 6. Sending Responses

Controllers determine:

- Status codes
- Response format

Example:

```javascript
res.status(201).json(book);
```

Possible responses:

| Status Code | Meaning |
|------------|----------|
| 200 | Success |
| 201 | Resource Created |
| 400 | Bad Request |
| 401 | Unauthorized |
| 403 | Forbidden |
| 404 | Not Found |
| 500 | Internal Server Error |

---

## Controller Example

```javascript
async function createBook(req, res) {

    const data = req.body;

    const result =
        await bookService.createBook(data);

    res.status(201).json(result);
}
```

---

# 3. Service Layer

## Definition

The Service Layer contains the application's business logic.

It is the brain of the application.

Controllers only coordinate.

Services make decisions.

---

## Core Rule

A service should know absolutely nothing about HTTP.

It should not handle:

- Request objects
- Response objects
- Headers
- Status codes

Bad:

```javascript
res.status(400).json(...)
```

inside service.

Good:

```javascript
throw new Error("Invalid User");
```

Controller handles HTTP.

---

## Responsibilities of Services

### Business Logic

Example:

User must be at least 18 years old.

```javascript
if(user.age < 18){
   throw new Error("Not eligible");
}
```

This belongs in Service.

---

### Orchestration

Services can coordinate multiple operations.

Example:

Creating an order:

```text
1. Validate inventory
2. Create order
3. Reduce stock
4. Generate invoice
5. Send email
```

All inside the service.

---

### External Integrations

Services often call:

- Payment gateways
- Email providers
- SMS providers
- Third-party APIs

Example:

```javascript
stripe.createPayment(...)
```

---

## Service Example

```javascript
async function createBook(data){

    const exists =
        await repository.findByTitle(data.title);

    if(exists){
        throw new Error("Book exists");
    }

    return repository.save(data);
}
```

---

# 4. Repository Layer

## Definition

Repositories handle communication with databases.

They isolate database-specific code from business logic.

---

## Why Repositories?

Without repositories:

```javascript
service {
   SQL query here
}
```

Business logic becomes mixed with database logic.

Repositories solve this problem.

---

## Responsibilities

### Create Queries

Example:

```sql
SELECT * FROM books;
```

### Insert Data

```sql
INSERT INTO books(...)
```

### Update Data

```sql
UPDATE books
SET title='New'
```

### Delete Data

```sql
DELETE FROM books
```

---

## Single Responsibility Principle

Repository methods should be predictable.

Bad:

```javascript
getBooks(optionalId)
```

Returns different structures.

Good:

```javascript
getBookById(id)

getAllBooks()
```

Separate methods.

---

## Repository Example

```javascript
async function save(book){

   return db.books.insert(book);

}
```

---

## Layer Interaction

```text
Controller
   ↓
Service
   ↓
Repository
   ↓
Database
```

Repositories never communicate directly with controllers.

---

# 5. Middlewares

## Definition

Middlewares are functions that execute before the request reaches the controller.

They form a chain.

```text
Request
 ↓
Middleware A
 ↓
Middleware B
 ↓
Middleware C
 ↓
Controller
```

---

## Purpose

Avoid duplication.

Imagine:

- Authentication
- Logging
- Rate limiting

on 500 endpoints.

Without middleware:

```text
Repeated 500 times
```

With middleware:

```text
Written once
```

---

## The next() Function

Middleware receives:

```javascript
(req,res,next)
```

Example:

```javascript
function logger(req,res,next){

   console.log(req.url);

   next();
}
```

Calling:

```javascript
next()
```

passes control to the next middleware.

---

## Early Termination

A middleware can stop execution.

Example:

```javascript
if(!token){

   return res.status(401)
             .json("Unauthorized");
}
```

No `next()`.

Controller never executes.

---

## Execution Order

Order matters.

Example:

```text
CORS
 ↓
Rate Limit
 ↓
Authentication
 ↓
Controller
```

Authentication should happen after request validation and security checks.

---

## Common Middleware Types

### 1. CORS Middleware

Controls who can access the API.

Checks:

```http
Origin: example.com
```

Unauthorized origins are blocked.

---

### 2. Security Headers

Adds:

```http
X-Frame-Options
Content-Security-Policy
```

Protects against attacks.

---

### 3. Rate Limiting

Prevents abuse.

Example:

```text
100 requests/minute
```

Exceeded:

```http
429 Too Many Requests
```

---

### 4. Authentication Middleware

Verifies:

- JWT tokens
- Session cookies
- API keys

Invalid token:

```http
401 Unauthorized
```

Valid token:

User data is attached to context.

---

### 5. Logging Middleware

Records:

- Method
- URL
- Duration
- Status code

Example:

```text
GET /books 200 12ms
```

---

### 6. Global Error Handler

Usually placed at the end.

Example:

```javascript
app.use(errorHandler);
```

Converts raw exceptions into structured responses.

Example:

```json
{
   "error":"Book Not Found"
}
```

---

# 6. Request Context

## Definition

Request Context is a storage area that exists only for one HTTP request.

Think of it as:

```text
Temporary Backpack
```

carried along the request journey.

---

## Why Context Exists

Requests pass through:

```text
Middleware
 ↓
Middleware
 ↓
Controller
 ↓
Service
```

These components are independent.

Context allows them to share information.

---

## Lifecycle

Request arrives:

```text
Context Created
```

Request finishes:

```text
Context Destroyed
```

Nothing survives afterward.

---

## Common Structure

Key-Value Storage:

```javascript
context = {
   userId: 10,
   role: "admin"
}
```

---

## Use Case 1: Authentication Data

Authentication Middleware:

```javascript
context.userId = decoded.userId;
context.role = decoded.role;
```

Controller:

```javascript
const userId =
    context.userId;
```

---

### Why This Is Secure

Never trust:

```json
{
   "userId":999
}
```

A malicious user can fake it.

Instead:

```javascript
userId =
context.userId;
```

comes from a verified token.

---

## Use Case 2: Request Tracing

Middleware generates:

```text
a8c5d3f2-b123...
```

Stores in context:

```javascript
context.requestId
```

Every log contains:

```text
requestId=a8c5d3f2
```

Making debugging easier.

---

## Use Case 3: Timeouts and Cancellation

Context can store:

```javascript
timeout = 5 seconds
```

If external API hangs:

```text
Request Cancelled
```

Protects server resources.

---

## Use Case 4: Database Transactions

Context can hold:

```javascript
transactionId
```

Shared across repositories.

Ensures operations succeed or fail together.

# Interview Questions

### Q1. Why do we need Controllers, Services, and Repositories?

To separate concerns, improve maintainability, testing, scalability, and code organization.

---

### Q2. Should business logic be inside Controllers?

No. Controllers should only coordinate requests and responses. Business logic belongs in Services.

---

### Q3. Why should Services be HTTP-independent?

Because business logic should remain reusable regardless of whether data comes from HTTP APIs, CLI tools, message queues, or scheduled jobs.

---

### Q4. What is the purpose of a Repository?

To abstract database operations and isolate SQL/database code from business logic.

---

### Q5. What happens if a middleware doesn't call `next()`?

The request lifecycle stops and the controller will never execute.

---

### Q6. Why is middleware order important?

Because requests pass through middleware sequentially, and earlier middleware can modify or block requests before later middleware runs.

---

### Q7. What is Request Context?

A request-scoped storage mechanism used to share data between middlewares, controllers, and services during a single request lifecycle.

---

### Q8. Why store `user_id` in Request Context instead of trusting the request body?

Because request bodies can be manipulated by users. Context values come from verified authentication mechanisms and are therefore trusted.

---

# Summary

A well-structured backend application follows a layered architecture:

- **Controllers** manage HTTP communication.
- **Services** contain business logic.
- **Repositories** communicate with databases.
- **Middlewares** execute reusable logic before controllers.
- **Request Context** allows safe sharing of request-specific data.

Together, these components create a backend system that is secure, scalable, maintainable, and easy to extend.
