# 1. What is REST? (History & Definition)

## The Origin

In the 1990s, **Tim Berners-Lee** invented the World Wide Web. As the web grew exponentially, it faced major scalability challenges.

In 2000, **Roy Fielding** proposed a standardized architectural style called **REST (Representational State Transfer)** to solve these problems and improve scalability, maintainability, and interoperability of web systems.

---

## Breaking Down the Name

### Representational

Resources on the web can have different representations depending on the client requesting them.

Examples:

- Browser → HTML
- Mobile App → JSON
- Another Service → XML or JSON

---

### State

State refers to the current condition of a resource.

Example:

A shopping cart may contain:

```json
{
  "items": 3,
  "totalPrice": 2500
}
```

This data represents the current state of the cart.

---

### Transfer

The client and server transfer resource representations using HTTP protocols and methods.

# 2. The 6 Constraints of REST Architecture

A system is considered truly RESTful only if it follows these six constraints defined by Roy Fielding.

---

## Constraint 1: Client-Server

Responsibilities are separated.

**Client:**

- User Interface (UI)
- User Experience (UX)

**Server:**

- Business Logic
- Data Storage
- Authentication
- Processing

Benefits:

- Independent development
- Easier maintenance
- Better scalability

---

## Constraint 2: Uniform Interface

All communication follows a standard and predictable structure.

Examples:

```http
GET /users
POST /users
GET /users/123
DELETE /users/123
```

Benefits:

- Consistency
- Simpler integrations
- Easier learning curve

---

## Constraint 3: Layered System

Applications can contain multiple intermediate layers.

Example:

```text
Client
   ↓
Load Balancer
   ↓
API Gateway
   ↓
Application Server
   ↓
Database
```

Each layer only knows about the layer directly beneath it.

Benefits:

- Improved security
- Better scalability
- Easier infrastructure management

---

## Constraint 4: Cache

Responses should indicate whether they can be cached.

Example:

```http
Cache-Control: max-age=3600
```

Benefits:

- Reduced server load
- Faster responses
- Lower network usage

---

## Constraint 5: Stateless

The server stores no client session state between requests.

Each request must contain all necessary information.

Example:

```http
GET /profile
Authorization: Bearer token
```

The server should not depend on previous requests.

Benefits:

- Easy horizontal scaling
- Improved reliability
- Simpler architecture

---

## Constraint 6: Code on Demand (Optional)

The server may send executable code to clients.

Example:

```html
<script src="app.js"></script>
```

JavaScript downloaded by browsers is a common example.

Benefits:

- Extends client functionality dynamically

---

# 3. Anatomy of a RESTful Route

## Standard Structure

A typical API endpoint:

```text
https://api.example.com/v1/books
```

Breakdown:

| Component | Meaning |
|-----------|---------|
| https | Secure protocol |
| api | API subdomain |
| v1 | API version |
| books | Resource |

---

## Always Use Plural Nouns

Correct:

```text
/books
/users
/organizations
```

Even for a single resource:

```text
/books/123
/users/5
```

Avoid:

```text
/book
/user
```

---

## URL Formatting Rules

Never use:

```text
/books/Harry Potter
/books/harry_potter
```

Use:

```text
/books/harry-potter
```

Rules:

- Lowercase letters
- Hyphens instead of spaces
- No underscores

---

## Hierarchical Nesting

Use `/` to express ownership relationships.

Example:

```text
/organizations/123/projects
```

Meaning:

> Fetch all projects belonging to organization 123.

More examples:

```text
/users/5/orders
/orders/100/items
```

# 4. HTTP Methods and Idempotency

## What is Idempotency?

An operation is idempotent when performing it multiple times produces the same server state as performing it once.

---

## GET (Idempotent)

Used to retrieve data.

Example:

```http
GET /users/123
```

Calling it 1000 times does not modify data.

---

## PATCH (Idempotent)

Used for partial updates.

Example:

```http
PATCH /users/123
```

Payload:

```json
{
  "status": "active"
}
```

Sending the same update repeatedly results in the same final state.

---

## PUT (Idempotent)

Used to replace the entire resource.

Example:

```http
PUT /users/123
```

Payload:

```json
{
  "name": "John",
  "email": "john@example.com"
}
```

Repeated requests yield the same resource state.

---

## DELETE (Idempotent)

Used to remove resources.

Example:

```http
DELETE /users/123
```

Behavior:

- First call → deletes resource
- Later calls → typically return `404 Not Found`

No additional side effects occur.

---

## POST (Non-Idempotent)

Used to create resources.

Example:

```http
POST /users
```

Every successful request creates a new record.

10 identical POST requests:

```text
10 Requests
→ 10 Users
→ 10 Different IDs
```

---

# 5. Custom Actions (Beyond CRUD)

Some actions do not fit:

- Create
- Read
- Update
- Delete

Examples:

- Clone Project
- Archive Organization
- Publish Blog
- Approve Invoice

These operations often trigger complex workflows.

---

## REST Rule

Use **POST** for custom actions.

Examples:

```http
POST /projects/123/clone
POST /organizations/5/archive
POST /posts/50/publish
POST /invoices/200/approve
```

Pattern:

```text
POST /resource/{id}/{action}
```

# 6. Designing Robust List APIs

Large datasets require three important features.

---

## 1. Pagination

Avoid returning thousands of records at once.

Bad:

```http
GET /users
```

Returning:

```json
100000 users
```

Good:

```http
GET /users?page=1&limit=10
```

---

### Example Response

```json
{
  "data": [],
  "total": 150,
  "page": 1,
  "totalPages": 15
}
```

Fields:

| Field | Description |
|-------|-------------|
| data | Current page records |
| total | Total records |
| page | Current page |
| totalPages | Maximum pages |

---

## 2. Sorting

Allow users to control ordering.

Example:

```http
GET /users?sortBy=name&sortOrder=ascending
```

Common fields:

```text
name
createdAt
updatedAt
price
rating
```

---

## 3. Filtering

Allow clients to request only relevant data.

Examples:

```http
GET /users?status=active
```

```http
GET /organizations?name=google
```

```http
GET /projects?status=completed
```

Multiple filters:

```http
GET /users?status=active&role=admin
```

---

# 7. Handling HTTP Status Codes Properly

## 200 OK

Used for:

- Fetching data
- Updating data
- Custom actions

Example:

```http
GET /users/123
```

Response:

```http
200 OK
```

---

## 201 Created

Used after successful resource creation.

Example:

```http
POST /users
```

Response:

```http
201 Created
```

---

## 204 No Content

Used after successful deletion.

Example:

```http
DELETE /users/123
```

Response:

```http
204 No Content
```

No response body is returned.

---

## 404 Not Found Rule

### Return 404 For Missing Single Resources

Example:

```http
GET /users/999
```

If user 999 does not exist:

```http
404 Not Found
```

---

### Do NOT Return 404 For Empty Lists

Example:

```http
GET /users?name=zack
```

No users found.

Correct response:

```http
200 OK
```

```json
[]
```

Reason:

The endpoint exists and was processed successfully.

The result is simply empty.

# 8. Golden Rules & Best Practices

## Extract Nouns from UI

Before designing APIs:

1. Study Figma or wireframes.
2. Identify business entities.
3. Convert entities into resources.

Example:

UI Contains:

- Users
- Projects
- Tasks
- Organizations

Resources Become:

```text
/users
/projects
/tasks
/organizations
```

---

## Implement Sane Defaults

Applications should behave sensibly even when optional inputs are missing.

Examples:

### Pagination

```text
Default limit = 10
```

### Sorting

```text
Default sortBy = createdAt
Default sortOrder = descending
```

### Entity Creation

```json
{
  "status": "active"
}
```

Used when status is omitted.

Benefits:

- Better user experience
- Fewer client-side bugs
- More resilient APIs

---

## Maintain Total Consistency

Choose conventions and never deviate.

Example:

Use:

```json
{
  "createdAt": "2025-01-01"
}
```

Avoid mixing:

```json
{
  "created_at": "2025-01-01"
}
```

in one endpoint and:

```json
{
  "createdAt": "2025-01-01"
}
```

in another.

Rules:

- Consistent naming
- Consistent casing
- Consistent response formats
- Consistent error structures

---

## Interactive Documentation

Always provide API documentation.

Recommended tools:

- Swagger UI
- OpenAPI Specification
- Postman Collections

Benefits:

- Faster frontend integration
- Easier testing
- Better developer experience
- Self-documenting APIs

# 10. Interview Questions

## Q1

What does REST stand for?

**Answer:**

Representational State Transfer. An architectural style for distributed hypermedia systems proposed by Roy Fielding in 2000.

---

## Q2

What are the 6 constraints of REST?

**Answer:**

1. Client-Server
2. Uniform Interface
3. Layered System
4. Cache
5. Stateless
6. Code on Demand (Optional)

---

## Q3

What is statelessness in REST?

**Answer:**

The server does not store any client session state between requests. Every request must carry all the information needed to process it.

---

## Q4

What is idempotency? Which HTTP methods are idempotent?

**Answer:**

An operation is idempotent when calling it multiple times produces the same server state as calling it once.

Idempotent methods: GET, PUT, PATCH, DELETE.

Non-idempotent: POST.

---

## Q5

Difference between PUT and PATCH?

**Answer:**

PUT replaces the entire resource.

PATCH updates only specific fields of the resource.

---

## Q6

When should you use POST for custom actions?

**Answer:**

When an operation does not map cleanly to CRUD — such as cloning, archiving, publishing, or approving — use POST with an action segment.

Example:

```http
POST /invoices/200/approve
```

---

## Q7

Should an empty list return 404?

**Answer:**

No. An empty list should return:

```http
200 OK
[]
```

404 is only for when the endpoint or specific resource does not exist.

---

## Q8

What are sane defaults in API design?

**Answer:**

Predefined values used when optional parameters are not provided by the client.

Examples: default page limit of 10, default sort order of descending by createdAt.

---

## Q9

Why should URLs use plural nouns?

**Answer:**

REST resources represent collections. Plural nouns are consistent whether accessing a list or a single item.

```text
/users      → collection
/users/123  → single item
```

---

## Q10

What is the correct status code after a successful DELETE?

**Answer:**

```http
204 No Content
```

The resource was deleted successfully and no body is returned.

---

## Q11

What is the Layered System constraint?

**Answer:**

The architecture can include multiple intermediate layers such as load balancers, API gateways, and caches. Each layer only interacts with the layer directly beneath it.

---

## Q12

Why is API versioning important?

**Answer:**

It allows breaking changes to be introduced without affecting existing clients. Old and new versions can coexist simultaneously.

Example:

```text
/api/v1/users
/api/v2/users
```
