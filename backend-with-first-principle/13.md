# 1. What is Caching?

## Definition

Caching is a technique used to **reduce the time and effort required to retrieve data or perform operations**.

---

## Simple Understanding

Caching means:

> Store a *small subset of frequently used data* in a *faster storage location* so it can be accessed quickly.

---

## Key Idea

- You don't store all data in cache
- Only *important and frequently accessed data*
- Stored in a *faster system (like RAM)*

---

## Why It Matters

Caching is critical for **high-performance applications**, especially those that require:

- Low latency (milliseconds or microseconds)
- Handling millions of users

---

# 2. Why Caching is Important

Caching is mainly used to:

- Avoid *repeated heavy computations*
- Avoid *fetching large data repeatedly*
- Reduce *server load*
- Improve *response time*

---

## Common Pattern

Caching is useful when:

1. Data is *expensive to compute*
2. Data is *frequently requested*
3. Data does *not change often*

---

# 3. Real-World Examples

## Google Search

Search queries involve *complex algorithms* (ranking, indexing).

Same queries are searched millions of times.

### Without Cache

- Recompute results every time
- High latency
- High server load

### With Cache

- Store results of popular queries
- If found → *Cache Hit → instant response*
- If not → *Cache Miss → compute + store*

---

## Netflix (CDN)

Netflix serves **huge video data globally**.

### Problem

Serving data from one location → high latency.

### Solution: CDN (Content Delivery Network)

- Store content at *edge servers (near users)*
- Serve data from the *nearest location*

### Key Idea

> Cache data geographically closer to users.

---

## Twitter (X) Trending Topics

Calculating trends requires:

- Processing millions of tweets
- Heavy computation

### Solution

- Compute trends periodically (e.g., every few minutes)
- Store results in cache
- Serve cached results instantly

---

# 4. Levels of Caching

There are *three main levels* of caching.

---

## Level 1: Network Level Caching

### A. CDN (Content Delivery Network)

- Stores content on *edge servers*
- Reduces latency by serving data from nearby locations

---

### How CDN Works

1. User requests a resource
2. DNS routes request to nearest *edge server*
3. Edge server checks:
   - If data exists → *Cache Hit → return instantly*
   - Else → fetch from origin → store → return

---

### TTL (Time To Live)

- Defines how long data stays in cache
- After expiry → fetch fresh data

---

### B. DNS Caching

DNS converts *domain names → IP addresses*.

### Why Cache DNS?

Without caching:

- Every request requires multiple server lookups

With caching:

- Faster resolution

### DNS Cache Levels

1. OS cache
2. Browser cache
3. ISP (recursive resolver) cache
4. Root/TLD servers

---

## Level 2: Hardware Level Caching

Caching also exists inside the **computer hardware**.

### Memory Hierarchy

```text
L1 Cache  (fastest)
L2 Cache
L3 Cache
RAM       (Main Memory)
Disk      (Slowest)
```

### Key Idea

- Closer to CPU → faster
- RAM is faster than disk

### Important Insight

- RAM is *fast but limited and volatile*
- Disk is *slow but persistent*

---

## Level 3: Software Level Caching

This is what backend engineers use daily.

### In-Memory Databases

Examples:

- Redis
- Memcached

### Why They Are Fast

- Store data in *RAM*
- No disk access needed

### Key Characteristics

- In-memory
- Key-value based
- No strict schema (NoSQL)

---

# 5. Caching Strategies

## Strategy 1: Lazy Caching (Cache Aside)

### Flow

1. Request comes
2. Check cache
3. If found → return
4. If not:
   - Fetch from DB
   - Store in cache
   - Return

### Key Idea

> Cache data *only when needed*.

---

## Strategy 2: Write Through

### Flow

When data is updated:

- Update *database*
- Update *cache at same time*

### Pros

- Cache is always *fresh*

### Cons

- Slower writes (extra work)

---

# 6. Cache Eviction Policies

Cache memory is limited, so old data must be removed.

---

## 1. No Eviction

- No removal policy
- Cache becomes full → errors

---

## 2. LRU (Least Recently Used)

- Remove data *not used recently*

---

## 3. LFU (Least Frequently Used)

- Remove data used *least number of times*

---

## 4. TTL (Time To Live)

- Data expires automatically after time limit

---

# 7. Use Cases of Caching (Redis / Memcached)

## 1. Database Query Caching

Cache results of *expensive queries*.

Examples:

- Complex JOIN queries
- Dashboard data

---

## 2. Session Storage

Store user session data in cache.

Why?

- Faster than database
- Reduces DB load

---

## 3. API Caching

Cache responses from external APIs.

Example:

- Weather API

Benefits:

- Reduces cost
- Avoids rate limits

---

## 4. Rate Limiting

Used to control number of requests per user.

### How It Works

1. Identify user (IP address)
2. Store request count in cache
3. Increment count on each request
4. If limit exceeded:

```http
429 Too Many Requests
```

### Why Use Cache Here?

- Very fast
- Avoids database load
- Needed for real-time counting

# 8. Interview Questions

## Q1

What is caching?

**Answer:**

A technique that stores frequently accessed data in a faster storage location to reduce retrieval time and computation overhead.

---

## Q2

When should you use caching?

**Answer:**

When data is frequently requested, expensive to compute, and does not change often.

---

## Q3

What is a Cache Hit and a Cache Miss?

**Answer:**

Cache Hit → requested data is found in cache, returned instantly.

Cache Miss → data not in cache, fetched from source, stored in cache, then returned.

---

## Q4

What is TTL?

**Answer:**

Time To Live. Defines how long data remains valid in cache before it expires and must be refreshed.

---

## Q5

Difference between Lazy Caching and Write Through?

**Answer:**

Lazy Caching populates the cache only when data is requested and not found.

Write Through updates both the database and cache simultaneously on every write.

---

## Q6

What are common cache eviction policies?

**Answer:**

- No Eviction
- LRU (Least Recently Used)
- LFU (Least Frequently Used)
- TTL (Time To Live)

---

## Q7

Why is Redis faster than a traditional database?

**Answer:**

Redis stores data in RAM. Traditional databases read from disk. RAM access is orders of magnitude faster than disk access.

---

## Q8

What is a CDN and how does it use caching?

**Answer:**

A Content Delivery Network stores content on edge servers located near users. When a user requests data, the nearest edge server serves it from cache instead of fetching from the origin server, reducing latency.

---

## Q9

How is caching used for rate limiting?

**Answer:**

Each user's request count is stored in cache with a TTL. On each request, the count is incremented. If it exceeds the limit within the TTL window, a `429 Too Many Requests` response is returned.

---

## Q10

What are the three levels of caching?

**Answer:**

1. Network Level — CDN, DNS caching
2. Hardware Level — CPU caches (L1, L2, L3), RAM
3. Software Level — Redis, Memcached

---

# 9. Key Takeaways

- Caching improves *performance and scalability*
- Use it when data is *frequently accessed* and *expensive to compute*
- RAM-based caching is *fast but limited*
- Always choose the correct *strategy* and *eviction policy*

Core Caching Flow:

```text
Request
   ↓
Check Cache
   ↓
Cache Hit?
   ↓
Yes → Return Instantly
No  → Fetch from DB → Store in Cache → Return
```
