# 1. The Limitation of Relational Databases

## The Librarian Analogy

Imagine a librarian who has no index and must check every single book to find the one you want.

That is exactly what a relational database does during a keyword search.

---

## The Problem

Standard SQL keyword search:

```sql
SELECT * FROM reviews
WHERE body LIKE '%javascript%';
```

Behavior:

```text
Row 1  → scan
Row 2  → scan
Row 3  → scan
...
Row 50,000 → scan
```

This is a **linear scan**.

---

## Why This is Slow

- Every row is checked regardless of relevance
- Performance degrades as data grows
- High latency on large datasets
- No ranking of results

Result:

```text
Keyword search on large tables
→ Several seconds of latency
```

---

# 2. The Inverted Index

## The Revolutionary Technique Behind Elasticsearch

Instead of scanning every document for a term, an inverted index maps every **word** to the specific **documents** where it appears.

---

## How It Works

Documents:

```text
Doc 1: "JavaScript is fast"
Doc 2: "Python is easy"
Doc 3: "JavaScript and Python are popular"
```

Inverted Index:

```text
"javascript" → [Doc 1, Doc 3]
"python"     → [Doc 2, Doc 3]
"fast"       → [Doc 1]
"easy"       → [Doc 2]
"popular"    → [Doc 3]
```

---

## Search Flow

Query:

```text
"javascript"
```

Lookup:

```text
→ [Doc 1, Doc 3]
```

No scanning.

Direct lookup.

```text
Linear Scan (SQL)   → O(n)
Inverted Index      → O(1) lookup
```

---

## Result

Lightning-fast lookups regardless of dataset size.

# 3. Relevance Scoring

## Beyond Basic Queries

Standard SQL returns results with no ranking.

Elasticsearch uses the **BM25 algorithm** to rank results by relevance.

---

## Factors That Affect Score

### Term Frequency

How many times does the search term appear in the document?

More occurrences → higher score.

---

### Document Frequency

How common is the term across all documents?

Rare terms → higher score (more meaningful).

---

### Document Length

Shorter documents with the term → higher score than long documents with the same term.

---

### Field Boosting

Different fields can be given different importance.

Example:

```text
Title match   → weight: 3x
Body match    → weight: 1x
```

A term found in the title ranks higher than the same term in the body.

---

## Result

```text
Query: "javascript tutorial"
      ↓
BM25 Scoring
      ↓
Ranked Results (most relevant first)
```

# 4. Typo Tolerance

## Handling User Input Errors Gracefully

Users make typos.

Standard SQL:

```sql
WHERE body LIKE '%javascrpit%'
```

Result:

```text
0 rows
```

---

## Elasticsearch Approach

Elasticsearch uses **fuzzy matching** and **edit distance** algorithms.

Query:

```text
"javascrpit"
```

Result:

```text
→ matches "javascript"
→ returns relevant documents
```

---

## Why This Matters

- Real users misspell words
- Search should be forgiving
- Better user experience
- Higher search success rate

# 5. Elasticsearch vs PostgreSQL — Benchmark

## Setup

- Dataset: 50,000 reviews
- Same keyword search on both systems

---

## PostgreSQL

Query:

```sql
SELECT * FROM reviews
WHERE body LIKE '%keyword%';
```

Result:

```text
Several seconds of latency
```

---

## Elasticsearch

Same search.

Result:

```text
Under 500–1000 milliseconds
```

---

## Comparison

| | PostgreSQL (LIKE) | Elasticsearch |
|--|-------------------|---------------|
| Method | Linear scan | Inverted index |
| Speed (50k rows) | Several seconds | < 1 second |
| Relevance ranking | No | Yes (BM25) |
| Typo tolerance | No | Yes |

# 6. Engineering Takeaway

## When to Use Standard SQL Search

- Small datasets
- Exact matches
- Simple filters

```sql
WHERE status = 'active'
WHERE email = 'john@gmail.com'
```

---

## When to Use Full-Text Search

- Large datasets
- Keyword search across text fields
- Relevance ranking needed
- Typo tolerance required

Examples:

- Product search
- Article search
- Review search
- Log search

---

## Options Available

### Elasticsearch

Dedicated search engine.

Best for large-scale, complex search requirements.

---

### PostgreSQL Full-Text Search

Built-in full-text search features.

```sql
WHERE to_tsvector('english', body)
   @@ to_tsquery('javascript');
```

Good for moderate search needs without adding a separate service.

---

## Decision Flow

```text
Small data + exact match
      → Standard SQL

Large data + keyword search + ranking
      → Elasticsearch or Postgres FTS
```

# 7. Interview Questions

## Q1

Why is `LIKE '%keyword%'` slow on large tables?

**Answer:**

It performs a full linear scan of every row regardless of the data size, resulting in O(n) complexity and high latency on large datasets.

---

## Q2

What is an Inverted Index?

**Answer:**

A data structure that maps every word to the list of documents where it appears. Instead of scanning documents for a term, you look up the term directly to get the matching documents instantly.

---

## Q3

What is BM25?

**Answer:**

A relevance ranking algorithm used by Elasticsearch that scores documents based on term frequency, document frequency, document length, and field boosting to return the most relevant results first.

---

## Q4

What is field boosting?

**Answer:**

Assigning different weights to different fields during search scoring. For example, a match in the title field can be weighted 3x more than a match in the body field, pushing title matches higher in results.

---

## Q5

How does Elasticsearch handle typos?

**Answer:**

Through fuzzy matching using edit distance algorithms. A search for "javascrpit" still returns results for "javascript" by allowing a configurable number of character edits.

---

## Q6

What was the performance difference between PostgreSQL and Elasticsearch in the benchmark?

**Answer:**

On 50,000 reviews, PostgreSQL took several seconds for a keyword search while Elasticsearch returned results in under 500–1000 milliseconds.

---

## Q7

When should you use Elasticsearch over standard SQL?

**Answer:**

When dealing with large datasets that require keyword search, relevance ranking, typo tolerance, or complex full-text queries that SQL LIKE cannot handle efficiently.

---

## Q8

What is the alternative to Elasticsearch inside PostgreSQL?

**Answer:**

PostgreSQL has built-in full-text search using `tsvector` and `tsquery`. It is suitable for moderate search needs without the overhead of running a separate Elasticsearch service.

---

## Q9

What is the time complexity difference between a SQL LIKE scan and an inverted index lookup?

**Answer:**

SQL LIKE performs O(n) linear scans. An inverted index lookup is effectively O(1) — the term is looked up directly in the index.

---

## Q10

What is the core engineering takeaway about search?

**Answer:**

Use standard SQL for exact matches and small datasets. Integrate a full-text search engine like Elasticsearch (or PostgreSQL FTS) when keyword search, ranking, and typo tolerance are required at scale.
