# 1. The Mindset of Fault Tolerance

In backend engineering, errors are not anomalies — they are inevitable.

- Databases will fail
- External APIs will time out
- Users will submit bad data
- Logic will encounter unpredicted edge cases

---

## The Shift in Thinking

Wrong question:

```text
"Will this fail?"
```

Right question:

```text
"How will the system behave when this fails?"
```

A fault-tolerant system is designed around the assumption that failure will happen.

---

# 2. Types of Backend Errors

---

## Logic Errors (The Most Dangerous)

Logic errors do not crash the application.

The code runs perfectly — but the business outcome is wrong.

Examples:

- Applying a discount twice
- Calculating negative shipping costs
- Granting incorrect permissions

### Why They Happen

- Misunderstood business requirements
- Poorly implemented algorithms
- Failure to account for edge cases

### Why They Are Dangerous

```text
No crash
No alert
No warning
      ↓
Runs unnoticed for weeks
      ↓
Quietly corrupts data or bleeds revenue
```

---

## Database Errors

The backend relies entirely on the database.

These errors can take down the entire application.

---

### Connection Errors

The backend cannot reach the database.

Causes:

- Network outages
- Server overload
- Exhausted connection pools

---

### Constraint Violations

Trying to perform an action the database rules forbid.

Examples:

```text
Unique Constraint → creating account with existing email
Foreign Key Violation → referencing an author ID that doesn't exist
```

---

### Query Errors

- Malformed SQL (typos)
- Timeouts on complex aggregations
- Deadlocks (circular dependencies between transactions)

---

## External Service Errors

Modern backends rely on third-party services:

- Auth0
- Stripe
- AWS S3
- Resend

Every dependency is a potential point of failure outside your control.

---

### Network Issues

- Connection timeouts
- DNS failures
- Routing partitions

---

### Authentication Rejections

External service rejects your API key.

Causes:

- Key expired
- Insufficient permissions

---

### Rate Limiting

```http
429 Too Many Requests
```

Often caused by a logic bug on your end spamming the service.

---

### Outages

External service completely goes down.

Nothing you can do except gracefully degrade.

---

## Input Validation Errors (Easiest to Handle)

Errors caused by consumers sending bad, malformed, or malicious data.

### Types

- **Format** — invalid emails or dates
- **Range** — passwords too short, arrays exceeding max length
- **Required Fields** — missing mandatory payload data

### Rule

Always handle at the entry point.

Return:

```http
400 Bad Request
```

---

## Configuration Errors

Errors that occur when moving between environments.

```text
Dev → Staging → Prod
```

Example:

```text
Forgetting to add OPENAI_API_KEY to production environment variables
```

### Best Practice

Validate all configuration variables at **startup**.

```text
App crashes immediately on deployment
      ↓
Better than failing silently during a user's request
```

# 3. Proactive Error Detection

The best error handling happens before the error impacts the user.

---

## Health Checks

Expose a `/health` or `/status` endpoint.

```http
GET /health
→ 200 OK
```

External monitoring tools ping this to ensure the server is alive.

---

## Deep Health Checks

Don't just check if the server is running.

Write scripts to test:

- Database is responding
- Response within acceptable latency limits

---

## External Service Pings

Run automated test transactions.

Examples:

- Test Stripe charges
- Internal test emails

Verify third-party connectivity before real users hit it.

---

## Monitoring & Observability

Track:

- Performance degradation (leading indicator of failure)
- Error rates
- Throughput
- Business metrics (e.g., sudden drop in successful checkouts)

Tools:

- Grafana
- Loki
- Structured JSON logging

---

# 4. Error Response Strategies

---

## Immediate Response

### Recoverable Errors

Examples: network timeout, rate limits.

Strategy:

```text
Retry with Exponential Backoff
      ↓
Wait 1 min → 2 mins → 4 mins
```

Be careful not to overwhelm an already stressed system.

---

### Non-Recoverable Errors

Examples: database failure.

Strategy: **Graceful Degradation**

```text
Contain the damage
      ↓
Serve cached data
Disable non-essential features
Provide alternative fallbacks
```

---

## Recovery Strategies

### Automatic Recovery

- Restarting dead processes
- Clearing corrupted caches
- Failing over to backup nodes

---

### Manual Recovery

Documented playbooks for human intervention during severe incidents.

---

### Data Recovery

Data is the most important asset.

Prioritize data integrity via:

- Regular backups
- Transaction logs
- Specialized recovery tools

---

# 5. Architectural Error Control

---

## Propagation & Error Boundaries

Do not let a bug in one service crash another.

Strategies:

- Use message queues (RabbitMQ) to decouple services asynchronously
- Catch low-level exceptions
- Wrap them with business context
- Bubble them up intentionally

---

## The Final Safety Net: Global Error Handling

Instead of handling HTTP responses in every individual function:

```text
Funnel all errors up to a single centralized Middleware layer
```

---

### How It Works

```text
Repository Layer  → throws raw database error
Service Layer     → throws logic error
Handler Layer     → throws validation error
      ↓
Global Error Middleware
      ↓
Identifies type
      ↓
Formats correct HTTP response
```

---

### Why It Is Crucial

**Reduces Redundancy:**

Write the response logic for a "Unique Constraint" error once, not 50 times.

---

**Prevents Leaks:**

Unhandled edge cases default to:

```http
500 Internal Server Error
```

Rather than crashing the server or leaking internal data.

---

# 6. Security Considerations in Error Handling

---

## Prevent Information Leakage

Never expose internal system details in API error messages.

### The Threat

Bad error response:

```json
{
  "error": "Unique constraint failed on index 'users_email_idx' in table 'public.users'"
}
```

A malicious actor now knows your database schema and can craft targeted attacks.

---

### The Fix

Global Error Handler intercepts detailed database errors.

Converts to:

```json
{
  "error": "Something went wrong."
}
```

---

## Authentication Endpoints

Be vague when rejecting login attempts.

### The Threat

Bad response:

```json
{
  "error": "Email not found"
}
```

An attacker can test millions of emails to discover which ones are registered, then brute-force the passwords.

---

### The Fix

Always return:

```json
{
  "error": "Invalid email or password."
}
```

---

## Sanitize Your Logs

Do not write sensitive user data to server logs.

### The Threat

If the log aggregation service is compromised, hackers steal plain-text sensitive data.

---

### The Fix

Never log:

- Raw passwords
- Credit card numbers
- Full email addresses
- API keys

Log instead:

- User IDs
- Correlation IDs

Maintains debugging context without compromising security.

# 7. Interview Questions

## Q1

What is the fault-tolerant mindset in backend engineering?

**Answer:**

Shifting from "Will this fail?" to "How will the system behave when this fails?" Errors are inevitable; the system must be designed to handle them gracefully.

---

## Q2

Why are logic errors the most dangerous type of backend error?

**Answer:**

Because they do not crash the application. The code runs successfully but produces wrong business outcomes — corrupting data or bleeding revenue silently for weeks without triggering any alerts.

---

## Q3

What is Exponential Backoff and when is it used?

**Answer:**

A retry strategy where the wait time between retries increases exponentially after each failure (e.g., 1 min → 2 mins → 4 mins). Used for recoverable errors like network timeouts and rate limits to avoid overwhelming a stressed system.

---

## Q4

What is Graceful Degradation?

**Answer:**

When a non-recoverable error occurs, the system contains the damage by serving cached data, disabling non-essential features, or providing fallbacks — rather than crashing entirely.

---

## Q5

Why should configuration variables be validated at startup?

**Answer:**

It is better for the application to crash immediately on deployment with a clear error than to fail silently during a live user request due to a missing environment variable.

---

## Q6

What is a Global Error Handler and why is it important?

**Answer:**

A centralized middleware that catches all errors thrown across the repository, service, and handler layers. It reduces redundancy (write error response logic once), prevents information leakage, and ensures unhandled cases return a safe 500 response instead of crashing the server.

---

## Q7

Why should authentication error messages be vague?

**Answer:**

Specific messages like "Email not found" allow attackers to enumerate valid emails through automated scripts. Generic messages like "Invalid email or password" prevent this.

---

## Q8

What is a deep health check?

**Answer:**

A health check that goes beyond verifying the server is running — it tests that the database is responding and within acceptable latency limits, and that external service connections are healthy.

---

## Q9

What should never be written to server logs?

**Answer:**

Raw passwords, credit card numbers, full email addresses, and API keys. Log User IDs or Correlation IDs instead to maintain debugging context without exposing sensitive data.

---

## Q10

What is the danger of leaking database error messages to API responses?

**Answer:**

Detailed messages like table names and index names expose internal schema details, enabling attackers to craft targeted SQL injection or enumeration attacks.

---

## Q11

What are the three types of recovery strategies?

**Answer:**

Automatic recovery (restarting processes, failing over to backup nodes), Manual recovery (human intervention via documented playbooks), and Data recovery (backups, transaction logs).

---

## Q12

How do message queues help with error boundaries between services?

**Answer:**

By decoupling services asynchronously, a failure in one service does not directly crash another. Tasks are queued and retried independently, containing the blast radius of failures.
