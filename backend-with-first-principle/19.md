# 1. What is Graceful Shutdown?

Stopping a server **politely** instead of abruptly.

```text
Abrupt stop:     kill process → in-flight requests die mid-way
Graceful stop:   finish current work → clean up → exit
```

## Why It Matters

Abrupt shutdown during a deployment can cause:

- **Data corruption** (half-written records)
- **Duplicate payments** (request ran but client never got the response, then retried)
- Leaked connections and locked resources

# 2. Process Lifecycle & Signals

An application runs as an **OS process**.

The OS and deployment tools talk to it using **signals**.

A graceful shutdown lets the process run cleanup code **before** exiting.

---

## Signal Types

| Signal | Meaning | Sent By | Catchable? |
|--------|---------|---------|-----------|
| **SIGTERM** | Polite request to terminate | Kubernetes, PM2, `kill <pid>` | Yes |
| **SIGINT** | User interrupt | `Ctrl+C` in terminal (dev) | Yes |
| **SIGKILL** | Force stop immediately | `kill -9`, OS as last resort | **No** |

```text
SIGTERM / SIGINT  →  "Please stop"   →  app can clean up
SIGKILL           →  "Stop NOW"      →  no cleanup possible
```

SIGKILL is the nuclear option — cannot be caught or ignored.

# 3. Connection Draining

Like a restaurant closing: **no new guests**, but current diners finish their meals.

```text
Shutdown signal received
        ↓
Stop accepting NEW requests
        ↓
Let IN-FLIGHT requests finish
        ↓
Close server
```

## Without Draining

```text
Request in progress (payment processing...)
        ↓
Server killed
        ↓
Payment charged, response lost
        ↓
User retries → duplicate payment
```

## With Draining

In-flight request completes and returns a response before the server stops.

# 4. Resource Cleanup

Release resources in **reverse order of acquisition**.

```text
Acquired:   1. DB connection  →  2. Cache connection  →  3. File handle
Released:   3. File handle    →  2. Cache connection  →  1. DB connection
```

## Resources to Clean Up

- File handles
- Database connections
- Network connections
- Background threads / queue consumers

## Why Reverse Order?

Later resources often depend on earlier ones. Closing the DB first could break a task still using it.

Failing to clean up causes **leaks** and **inconsistent state**.

# 5. Graceful Shutdown in Java

## JVM Shutdown Hook

The JVM runs registered hooks on **SIGTERM** and **SIGINT**.

```java
public class Main {

    public static void main(String[] args) throws Exception {

        ExecutorService executor = Executors.newFixedThreadPool(4);

        Runtime.getRuntime().addShutdownHook(new Thread(() -> {
            System.out.println("Shutdown signal received...");

            executor.shutdown();   // stop accepting new tasks

            try {
                // wait for in-flight tasks
                if (!executor.awaitTermination(30, TimeUnit.SECONDS)) {
                    executor.shutdownNow();   // force after timeout
                }
            } catch (InterruptedException e) {
                executor.shutdownNow();
            }

            System.out.println("Cleanup complete");
        }));

        // ... start server / submit tasks
    }
}
```

Hooks do **not** run on SIGKILL.

# 6. Graceful Shutdown in Spring Boot

## Enable It

`application.properties`:

```properties
server.shutdown=graceful
spring.lifecycle.timeout-per-shutdown-phase=30s
```

## What Happens

```text
SIGTERM received
      ↓
Web server stops accepting new requests
      ↓
In-flight requests allowed to finish (up to 30s)
      ↓
Beans destroyed (@PreDestroy, DisposableBean)
      ↓
Application exits
```

## Cleanup Logic with @PreDestroy

```java
@Component
public class ConnectionManager {

    @PreDestroy
    public void cleanup() {
        System.out.println("Closing connections...");
        // close DB / cache / file handles
    }
}
```

The default is `server.shutdown=immediate`, so graceful must be turned on.

# 7. Shutdown Flow (Kubernetes)

```text
Deployment starts new pods
        ↓
Kubernetes sends SIGTERM to old pod
        ↓
Pod removed from load balancer (no new traffic)
        ↓
App drains in-flight requests
        ↓
App releases resources
        ↓
App exits cleanly
```

If the app doesn't exit within the **grace period** (default 30s):

```text
Kubernetes sends SIGKILL → forced stop
```

Set the timeout in Spring slightly **below** the Kubernetes grace period so cleanup finishes first.

# 8. Interview Questions

## Q1

What is graceful shutdown?

**Answer:**

Stopping a server by finishing ongoing work and releasing resources before exiting, instead of terminating abruptly.

---

## Q2

Why is graceful shutdown important?

**Answer:**

It prevents data corruption, duplicate payments, and resource leaks during deployments or restarts.

---

## Q3

Difference between SIGTERM, SIGINT, and SIGKILL?

**Answer:**

SIGTERM: polite termination request (Kubernetes, PM2). SIGINT: user interrupt (Ctrl+C). SIGKILL: forced immediate stop that cannot be caught or ignored.

---

## Q4

Can you handle SIGKILL in your application?

**Answer:**

No. It's handled directly by the OS, so no shutdown hooks or cleanup code can run.

---

## Q5

What is connection draining?

**Answer:**

Refusing new requests while allowing in-flight requests to complete before shutting down — like a restaurant that stops seating guests but lets current diners finish.

---

## Q6

In what order should resources be released?

**Answer:**

Reverse order of acquisition, because later resources may depend on earlier ones.

---

## Q7

How do you implement graceful shutdown in plain Java?

**Answer:**

Register a shutdown hook with `Runtime.getRuntime().addShutdownHook(...)`, stop accepting new tasks (`executor.shutdown()`), wait with `awaitTermination`, then release resources.

---

## Q8

How do you enable graceful shutdown in Spring Boot?

**Answer:**

Set `server.shutdown=graceful` and configure `spring.lifecycle.timeout-per-shutdown-phase`. Use `@PreDestroy` for custom cleanup.

---

## Q9

What happens if the app doesn't exit within Kubernetes' grace period?

**Answer:**

Kubernetes sends SIGKILL and force-terminates the process, risking interrupted work.

---

## Q10

How can abrupt shutdown cause duplicate payments?

**Answer:**

The payment may complete on the server, but the process dies before the response reaches the client. The client assumes failure and retries, charging again.
