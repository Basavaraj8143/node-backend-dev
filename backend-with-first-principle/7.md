# 1. Introduction

Modern applications rarely run on a single machine.

A typical system consists of:

```text
Frontend
   |
Internet
   |
Backend
   |
Database
```

Each component needs to exchange data.

However, computers do not naturally understand each other's internal data structures.

This creates a communication challenge.

Serialization and deserialization solve this problem.

They allow completely different systems, programming languages, and platforms to exchange information reliably.

---

# 2. The Core Problem in Distributed Systems

Consider a modern web application.

Frontend:

```text
JavaScript
```

Backend:

```text
Rust
```

Database:

```text
PostgreSQL
```

Each system represents data differently.

---

## JavaScript Object

```js
const user = {
  id: 1,
  name: "John"
};
```

---

## Rust Struct

```rust
struct User {
    id: i32,
    name: String,
}
```

---

Although they represent the same information, their internal memory layouts are completely different.

A Rust server cannot directly understand:

```js
{
  id: 1,
  name: "John"
}
```

as a JavaScript object.

The internet cannot transport language-specific objects.

A common format is required.

---

# 3. Why Serialization Exists

Serialization creates a universal language.

Instead of sending:

```text
JavaScript Objects
```

or

```text
Rust Structs
```

systems agree on a standard format.

Example:

```json
{
  "id": 1,
  "name": "John"
}
```

Now:

- JavaScript can create it.
- Rust can read it.
- Python can read it.
- Go can read it.
- Java can read it.

Serialization enables interoperability.

---

# 4. What is Serialization?

Serialization is:

> Converting native application data into a standard transferable format.

---

## Example

Native JavaScript Object:

```js
const user = {
  id: 1,
  name: "John"
};
```

Serialized JSON:

```json
{
  "id": 1,
  "name": "John"
}
```

The object becomes a text representation suitable for network transmission.

---

# Real Definition

```text
Native Data
     ↓
Serialization
     ↓
Transfer Format
```

---

# Why Serialize?

Networks do not transmit:

- Objects
- Classes
- Structs

Networks transmit:

```text
Bytes
```

Serialization converts application data into transferable bytes.

---

# 5. What is Deserialization?

Deserialization is the reverse process.

Definition:

> Converting a standard transfer format back into native application data.

---

## Example

Incoming JSON:

```json
{
  "id": 1,
  "name": "John"
}
```

Deserialized into:

### JavaScript

```js
{
  id: 1,
  name: "John"
}
```

---

### Rust

```rust
User {
   id: 1,
   name: "John"
}
```

---

# Process

```text
Transfer Format
      ↓
Deserialization
      ↓
Native Data
```

---

# 6. Serialization vs Deserialization

| Serialization | Deserialization |
|--------------|----------------|
| Native → Transfer Format | Transfer Format → Native |
| Before Sending | After Receiving |
| Encoding | Decoding |
| Outbound Data | Inbound Data |
| Client or Server | Client or Server |

---

# Easy Memory Trick

Serialization:

```text
Application → Network
```

Deserialization:

```text
Network → Application
```

---

# 7. Language Barriers in Networking

Different languages have different rules.

Example:

## JavaScript

```js
{
  age: 25
}
```

No strict typing.

---

## Rust

```rust
age: i32
```

Strict typing.

---

## Java

```java
Integer age;
```

Different implementation.

---

Without serialization:

```text
JavaScript
      X
Rust
```

Communication fails.

---

With serialization:

```text
JavaScript
      |
    JSON
      |
Rust
```

Communication succeeds.

# 8. Common Serialization Formats

Serialization standards fall into two categories:

---

# Text-Based Formats

Human readable.

Examples:

- JSON
- XML
- YAML
- CSV

---

# Binary Formats

Machine optimized.

Examples:

- Protobuf
- Avro
- MessagePack
- BSON

---

# Comparison

| Feature | Text Formats | Binary Formats |
|----------|-------------|-------------|
| Human Readable | Yes | No |
| Easy Debugging | Yes | No |
| Compact Size | Medium | High |
| Speed | Moderate | Fast |
| REST APIs | Common | Rare |
| Microservices | Sometimes | Very Common |

---

# 9. Text-Based Formats

Text formats can be read directly by humans.

---

## JSON

```json
{
  "name": "John"
}
```

Most popular.

---

## XML

```xml
<user>
  <name>John</name>
</user>
```

Common in older enterprise systems.

---

## YAML

```yaml
name: John
```

Common for configuration files.

---

# Benefits

- Human readable
- Easy debugging
- Easy logging
- Simple learning curve

---

# Drawbacks

- Larger payloads
- More bandwidth
- Slower parsing

---

# 10. Binary Formats

Binary formats are optimized for efficiency.

Humans cannot read them directly.

---

## Protobuf

Created by Google.

Example use:

- gRPC
- Microservices
- Internal APIs

---

## Avro

Common in:

- Kafka ecosystems
- Big Data systems

---

# Benefits

- Smaller payload size
- Faster transmission
- Faster parsing

---

# Drawbacks

- Harder debugging
- Not human readable
- Requires schemas

# 12. JSON Syntax Rules

JSON follows strict syntax rules.

---

# Rule 1

Must begin with:

```json
{
```

and end with:

```json
}
```

---

# Rule 2

Keys must be strings.

Valid:

```json
{
  "name": "John"
}
```

Invalid:

```json
{
  name: "John"
}
```

---

# Rule 3

Keys must use double quotes.

Correct:

```json
"name"
```

Incorrect:

```json
'name'
```

---

# Rule 4

Key-value pairs separated by colon.

```json
{
  "name": "John"
}
```

---

# Rule 5

Pairs separated by commas.

```json
{
  "name": "John",
  "age": 25
}
```

---

# 13. JSON Data Types

JSON supports only a limited set of types.

---

# String

```json
{
  "name": "John"
}
```

---

# Number

```json
{
  "age": 25
}
```

---

# Boolean

```json
{
  "active": true
}
```

---

# Array

```json

  "skills": ["JS", "Rust"]
```

---

# Object


# Null

```json
{
  "phone": null
```

# Unsupported Types

JSON cannot directly store:

```text

Classes
Methods
Pointers
References
```

# 14. Serialization in HTTP APIs

When sending a request:

```http
POST /users
```

Request body:

```json
{
  "name": "John"
}
```

The client serializes data before transmission.

---

Server receives:

```json
{
  "name": "John"
}
```

and deserializes it.

---

After processing:

```json
{
  "id": 1,
  "name": "John"
}
```

Server serializes response.

Client deserializes response.

---

# Request Flow

```text
Object
   ↓
Serialize
   ↓
JSON
   ↓
HTTP Request
```

---

# Response Flow

```text
HTTP Response
   ↓
JSON
   ↓
Deserialize
   ↓
Object
```

# 22. Summary

Serialization and deserialization are the foundation of communication between distributed systems.

Core workflow:

```text
Native Data
      ↓
Serialization
      ↓
Transfer Format
      ↓
Network
      ↓
Transfer Format
      ↓
Deserialization
      ↓
Native Data
```

Key Takeaways:

- Serialization = Encoding data for transmission
- Deserialization = Decoding received data
- JSON is the dominant format for REST APIs
- Binary formats like Protobuf optimize performance
- Serialization enables language-independent communication
- Backend engineers primarily work with serialized data at the Application Layer

Golden Rule:

> "Machines do not exchange objects, classes, or structs. They exchange serialized data."
